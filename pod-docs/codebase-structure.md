# Codebase structure

_For agents: scout writes it and engineers read it before coding. You check it and fix what's wrong._

> High-level overview only — what the system is and how its parts fit. No file lists or deep directory trees: those change every sprint, and agents read the code for detail. Name a path only for a part's top-level folder.

The **`## Smoke recipe`** below tells each engineer how to bring the app up for browser verification (per `pod:engineer`'s instructions). Fill it in — without it, engineers can't verify their slices and cap confidence at `medium`.

## What it is

OpenAFlow (repo `alvionlabs/openaflow`) is a local web app that shows every pod run across a developer's repos: each run's stage, the current wave's slices, what needs the human, and each engineer's live activity. Its actions merge a PR waiting on you, through `gh`, append your answer to a queue entry waiting on you, and resume a run's own Claude session with `continue` or `go`. One person runs it on their own machine.

## Parts

- `model` (packages/model) — `@openaflow/model`: parsers for pod's docs and the run model built from them. Pure TypeScript, used as source through its package `exports`, with no build step.
- `server` (packages/server) — `@openaflow/server`: Hono API server on Node, started with `tsx` in dev. `pnpm build` also bundles it into one folder, `packages/server/dist/app` (`server.mjs` with every dependency inside, and `web/`, the web build), which runs alone with `node server.mjs` and serves the web app and the API on one port. Finds repos (its config file plus pod's port claims), reads their pod docs and agent transcripts, asks `gh` about live PRs, watches the files with chokidar, and serves the Board at `/api/board` and as server-sent events at `/api/events`. Every route sits behind a request guard (loopback `Host` on the API or web port, in production the bound port; `Origin` too for writes); in production it also finds `git`, `gh`, and `claude` with no terminal, and answers `GET /api/tools` and `POST /api/actions/tool-path` (`pod-docs/feature-details/server.md`); routes under `/api/actions/` (remove-repo, which takes a repo out of the board's config, and forget-run, which deletes one run's leftover port claim, included) and `POST /api/repos` also need a POST of a JSON object with the per-launch session token (`X-OpenAFlow-Token`). The action routes (merge-preview, merge, answer, resolve) and the action log are in `pod-docs/feature-details/actions.md`. The resume and auto-continue routes, the toggle store, the idle check, and the automatic check that sends `continue` to toggled runs (through `claude -p --resume`) are in `pod-docs/feature-details/resume.md`. See `pod-docs/feature-details/server.md`.
- `web` (packages/web) — `@openaflow/web`: React + Vite single-page app, the desktop app's interface and the agents' test bench (no PWA manifest). Screen 1 (a full-height sidebar with the title, the runs list, and `Add repo`, which opens the Windows Select Folder dialog in the desktop app (through `desktop-bridge`) or a path field in the shared modal in the browser build; and the selected run's header with the ⋯ menu, the run's flow, the Next step card, and Waiting and Log tabs) reads the Board over `/api/events` and runs it through the model's `listRuns` and `buildPipeline`. Screen 2, the wave board (`screens/board`), builds on the same pipeline log; the URL hash picks the run, the view, and an open slice (`selection`). Screen 3, the engineer view (`screens/engineer`), sits under the board when a slice is open and fetches its engineer's tool timeline (`timeline-loader`) each time the agent's `lastAt` moves on the Board. Logic lives in tested `.ts` modules (`board-stream`, `selection`, `add-repo`, `timeline-loader`, each screen's `view.ts` or `board-view.ts`, and screen 1's `next-step`, `plan-view`, `tab-memory`, `add-repo-flow`, and `desktop-bridge`); components are glue. See `pod-docs/feature-details/wave-board.md` and `engineer-view.md`. Screen CSS uses only the theme's tokens.

- `desktop` (packages/desktop) — `@openaflow/desktop`: the Electron main process, with `electron` pinned to one exact version. It runs the server bundle in a `utilityProcess`, reads the port from the ready message, restarts a failed server once, and owns the quit. A quit never ends a resumed `claude`. It shows the board in a normal window and keeps a tray icon: a close hides the window, and the tray's menu has Open and Quit. Off-origin links go to the system browser. Only `main.ts` and `*-main.ts` files import `electron`; all logic sits in plain modules with fakes. `pnpm build` bundles the main process into `dist/main.cjs`. `pnpm dev` doesn't start it. `pnpm package` makes its per-user Windows installer. See `pod-docs/feature-details/desktop.md`.

## How they connect

In dev, the browser loads the web app from the Vite dev server, which proxies `/api` to the API server. In production, one process on one port answers the page, its files, and `/api`, and puts the session token in the page. The server reads repo files and transcripts and hands their text to `model`, which returns the run model and agent runs; the server sends the Board to the web app as JSON, and again over SSE whenever it changes. `model` never reads files itself. No database: state is rebuilt from files on start and kept in memory. The server writes its own config (the registered repos, added by Add repo and removed by Remove repo), in dev at each start its session token next to it (which the Vite dev server puts in the page; production keeps the token in memory and writes no file), and the action log `actions.jsonl`, the auto-continue toggles `auto-continue.json`, the chosen tool paths `tool-paths.json` (production), the auto-continue owner file `auto-continue-owner.json`, and the resume runs' stderr logs (`resume-logs/`) in the same folder. In a repo it writes one file, one line at a time: an answer appended to a line of `pod-docs/handoff-queue.md`, or (Close and Keep) that line's `**Resolution:** pending` rewritten. Its other outside changes are `gh pr merge`, on a PR waiting on you, and `claude -p --resume <session> <word>`, on a run's own session, with your login.

## Stack & conventions

- TypeScript everywhere, `strict` with `noUncheckedIndexedAccess`, ESM, Node 22 or later. Shared compiler options are in `tsconfig.base.json`; each package's `tsconfig.json` extends it and runs `tsc` with no emit. Imports of local files keep the `.ts` extension.
- pnpm workspace; the pnpm version is pinned in `package.json` (`packageManager`). Use pnpm only; `pnpm-lock.yaml` is the one lockfile.
- Vitest, one root config (`vitest.config.ts`) that runs `packages/*/src/**/*.test.ts` and `packages/*/test/**/*.test.ts`.
- **`model` has no I/O.** Nothing under `packages/model/src/` imports `node:*` builtins, `fs`, `path`, `child_process`, or network code. `packages/model/test/no-io.test.ts` enforces it. Tests under `packages/model/test/` may read files.
- Env, all optional: `OPENAFLOW_CONFIG_DIR` (folder for the board's `config.json`; default `%APPDATA%\openaflow-server`, `~/Library/Application Support/openaflow-server`, or `$XDG_CONFIG_HOME/openaflow-server`; with it unset, the first start copies the old folder of the same place once, see `pod-docs/feature-details/server.md`), `OPENAFLOW_PORTS_DIR` (pod's claim files; default `<os temp>/pod-ports`), `OPENAFLOW_CLAUDE_DIR` (default `CLAUDE_CONFIG_DIR`, else `~/.claude`), `OPENAFLOW_TRANSCRIPT_DAYS` (default 30), `OPENAFLOW_POLL=1` (watch by polling), `OPENAFLOW_CLAUDE_BIN` (the `claude` the resume runner starts; default `claude` on `PATH`; in production that absolute path only, else the tool finder's search), `OPENAFLOW_DESKTOP_DATA_DIR` (the shell's own data folder: Chromium's data, the single-instance lock, and the window state; default Electron's own folder; never the server's config folder), `OPENAFLOW_PARENT_PID` (production only: the parent's process ID, polled every 2 s; the server stops when that process is gone; unset or empty, no watch). A bad value stops the server with an error naming the variable.
- Ports come from env: `OPENAFLOW_API_PORT` (default `3000`) and `OPENAFLOW_WEB_PORT` (default `3001`). Both servers bind to `127.0.0.1` only. Production (`pnpm start`) has one port and doesn't read `OPENAFLOW_WEB_PORT`: `OPENAFLOW_API_PORT` is that port, with no fallback; unset or empty, it tries `47800` and takes a free port from the OS if that one is busy. An invalid port stops the process with an error naming the variable (`portFromEnv` in the server's config module, which the Vite config also uses).
- A test that starts the real Electron binary lives in a `real-*.test.ts` file, under `describe.runIf(process.env.OPENAFLOW_REAL_ELECTRON === '1' && process.platform === 'win32')`. `pnpm verify` skips it. `pnpm test:electron` runs it after `pnpm build`.
- A test that installs the real app lives in a `proof-*.test.ts` file in `packages/desktop/src`, under `describe.runIf(process.env.OPENAFLOW_REAL_INSTALL === '1' && process.platform === 'win32')`. `pnpm verify` and `pnpm test:electron` skip it. `pnpm test:install` runs it.
- `.gitattributes` forces LF line endings so fixtures check out the same on every OS.
- No linter yet.

## CI

`.github/workflows/pod-ci.yml` runs on every `pull_request` (any base branch) and on `push` to `pod-staging`:

- **verify** — on `windows-latest` only (the board is built for Windows first) with Node 22 and pnpm (`pnpm/action-setup`): `pnpm install --frozen-lockfile`, then `pnpm verify`.

No macOS or Linux run and no secret scan; see `pod-docs/decisions.md` (2026-10-22, Windows-only CI).

`.github/workflows/release.yml`, named `release`, starts only on a pushed tag `v<major>.<minor>.<patch>`. No agent pushes a tag or runs this workflow.

- **build** (`contents: read`): checks the tag against `version` in `packages/desktop/package.json` (`pnpm release:check --tag=<tag>`), then runs `pnpm verify`, `pnpm package`, and `pnpm release:check packages/desktop/release`. Then it uploads the installer, its blockmap, and `latest.yml`.
- **publish** (`contents: write`, needs **build**): has no checkout and runs no code from the repo. It downloads the three files and runs `gh release create` as a normal release. The token is on that step only. If a release for the tag exists, the command fails and overwrites nothing.

**Unproved until the human's first tag:** the workflow itself on GitHub, `pnpm release:check`'s install and launch on `windows-latest`, and the updater's GitHub provider. `pnpm test:install` proves the check on this machine only, and actionlint reads the file with no run. The steps for the first tags are in `pod-docs/feature-details/installer-and-updates.md`, under **First release: the human's hand-off**.

Each action is pinned to a full commit SHA. To update one, change the SHA and the version comment together. The installer's size limits are in `packages/desktop/src/release-rules.ts`: when the app gains or loses something large, measure again and change them.

## Smoke recipe

- **Install:** `pnpm install` (Node 22 or later; run `corepack enable pnpm` first if pnpm is missing).
- **Start commands:** both servers together with `pnpm dev`. Always point the board's config and claims at temp folders, so a run never touches the real config or pod's live claims: `OPENAFLOW_CONFIG_DIR=<tmp>/cfg OPENAFLOW_PORTS_DIR=<tmp>/ports OPENAFLOW_API_PORT=<api> OPENAFLOW_WEB_PORT=<web> pnpm dev` (PowerShell: `$env:OPENAFLOW_CONFIG_DIR='<tmp>\cfg'; $env:OPENAFLOW_PORTS_DIR='<tmp>\ports'; $env:OPENAFLOW_API_PORT='<api>'; $env:OPENAFLOW_WEB_PORT='<web>'; pnpm dev`). Separately: `pnpm --filter @openaflow/server dev` and `pnpm --filter @openaflow/web dev`, with the same env. Ready when the log shows `openaflow API listening on http://127.0.0.1:<api>` and Vite's `Local: http://127.0.0.1:<web>/`. Transcripts are read (never written) from `~/.claude`; set `OPENAFLOW_CLAUDE_DIR` to an empty temp folder to leave them out.
- **Production start:** `pnpm build`, then, with the same temp folders and one port: `OPENAFLOW_CONFIG_DIR=<tmp>/cfg OPENAFLOW_PORTS_DIR=<tmp>/ports OPENAFLOW_CLAUDE_DIR=<tmp>/claude OPENAFLOW_API_PORT=<port> pnpm start`. Ready when the log shows `openaflow API listening on http://127.0.0.1:<port>`. The page and the API are both on `<port>`, and the `<web>` and `<api>` of the URLs below are both `<port>`. Production writes no `session-token` file, so read the token from the page: `TOKEN=$(curl -s http://127.0.0.1:<port>/ | grep -o 'openaflow-token" content="[^"]*' | cut -d'"' -f3)`, then send `-H "X-OpenAFlow-Token: $TOKEN"`. It changes at each start. A second server on one config folder runs with no automatic check: its log names the first's process ID and the folder, and it stays off until it restarts. The bundle also runs alone: copy `packages/server/dist/app` anywhere and run `node server.mjs`. To stop it, send `{ type: 'openaflow:stop' }` over a `fork` channel, or start it with `OPENAFLOW_PARENT_PID` and end that process, or use Ctrl+C, or `taskkill /F /PID <pid>` (a forced end, so it leaves a stale `auto-continue-owner.json`, which the next start takes over). Then check the port. A stop never ends a resumed `claude`.
- **Desktop shell:** `pnpm build`, then, with the production start's temp folders and port, also set `OPENAFLOW_DESKTOP_DATA_DIR=<tmp>/shell` and run `pnpm desktop`. Ready when the log shows the same `openaflow API listening` line; the shell sets no port. The window opens on the board at that port; `--hidden` after the app's folder starts in the tray with no window. A close hides the window, and a second `pnpm desktop` on that data folder brings it back. To quit, use the tray's Quit. To reach the setup check with an install link, first put a `tool-paths.json` that names a `gh` path with no file there in the temp config folder. A login item, which nothing in the app writes today, lives under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` as the value `com.alvionlabs.openaflow`; the proofs set it with `reg add`. To register a repo and read the token, use the production start's curls on that port. The real exit proofs: `pnpm test:electron`, on Windows with a display, after `pnpm build`. They use temp folders and `fake-claude.mjs`. In a real run, a `claude.cmd` that names a script needs a `node.exe` beside it or a `node` on the merged `Path`. To stop a run, end only the process IDs you started: a forced end of the main process also ends the server, and it leaves `auto-continue-owner.json` for the next start's stale check.
- **Installed build:** `pnpm package` makes `packages/desktop/release/openaflow-setup-<version>.exe`, with its blockmap and `latest.yml`, and publishes nothing. electron-builder 26.18.1 downloads no winCodeSign archive, so no signing-tool setting applies (this machine has Developer Mode on, so that isn't proved without it). It takes about a minute, and the first run downloads Electron and NSIS. `pnpm test:install`, on Windows with a display, after `pnpm package`, installs per-user in a temp folder, runs the exe with temp folders, uninstalls, and prints `state diff: []`. Its first test runs `pnpm package` again, under the lock. Set `OPENAFLOW_PROOF_PORT` for its port (default `3100`). It stops when OpenAFlow is already installed for this user. To try it by hand: `openaflow-setup-<version>.exe /S /D=<tmp>\install`, then start `<tmp>\install\OpenAFlow.exe` with the desktop shell's env. Never run it with no temp env: it would open the real config folder. To stop it, end its recorded process ID, run `<tmp>\install\Uninstall OpenAFlow.exe /currentuser /S`, wait for the folder to go, and delete `%LOCALAPPDATA%\openaflow-updater`.
- **Release check:** `pnpm release:check <output dir>` checks a `pnpm package` output: one installer, its size, `latest.yml`, and the blockmap. Then it installs the build per-user in a temp folder, checks that the installed asar's `main.cjs` holds no `OPENAFLOW_UPDATE_TEST`, starts the exe with temp folders, waits for `/api/health`, and uninstalls in every case. It publishes nothing, and it ends with `state diff: []`. A failure exits non-zero with `release check failed at <step>`. It takes a free port unless `OPENAFLOW_PROOF_PORT` names one, and it refuses to run when OpenAFlow is already installed. `pnpm test:install packages/desktop/src/proof-release` proves the check on a good build and on three bad ones. It needs an installer in `packages/desktop/release` first, as all of `pnpm test:install` does.
- **Tool routes (production only; dev answers 404; a check only looks for files and starts no tool):** `curl -s http://127.0.0.1:<port>/api/tools -H "X-OpenAFlow-Token: $TOKEN"` → `200 {"tools":[…]}` in the order git, gh, claude, each `found`, `missing`, or `bad-path`; no token → `403 {"error":"bad token"}`. To choose a path: `curl -s -X POST http://127.0.0.1:<port>/api/actions/tool-path -H "Origin: http://127.0.0.1:<port>" -H "Content-Type: application/json" -H "X-OpenAFlow-Token: $TOKEN" --data-binary @<tmp>/body.json`, with `{"tool":"gh","path":"<absolute path to a fake gh.exe>"}` in the body file → `200` with `source: "settings"`, saved in `<tmp>/cfg/tool-paths.json`; `"path":null` clears it; a wrong one → `400 {"error":"wrong tool"}` or another rule word. To start with no terminal, spawn `server.mjs` from a small Node script with `detached: true`, `stdio: 'ignore'`, `Path` empty, and `SystemRoot` kept. Without `SystemRoot`, the registry read counts as empty.
- **DB setup:** none. To get a repo with pod docs to look at, copy a fixture: `cp -r packages/model/fixtures/chess-web <tmp>/chess-web`.
- **Login credentials:** none. **Session token:** the API writes a new one at each start to `<tmp>/cfg/session-token`; the page gets it in a meta tag (`curl -s http://127.0.0.1:<web>/ | grep openaflow-token`). Action curls (`POST /api/actions/...`) need `-H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)"` plus the `Origin` and `Content-Type: application/json` headers; without the token → `403 {"error":"bad token"}`. Never paste the token into logs or docs.
- **Merge routes (never merge a real PR in a smoke run):** take the repo id from `/api/board` (`repos[].id`). `curl -s -X POST http://127.0.0.1:<api>/api/actions/merge-preview -H "Origin: http://127.0.0.1:<api>" -H "Content-Type: application/json" -H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)" -d '{"repoId":"<id>","number":999}'` → `404 {"error":"not waiting on you"}`; the same request with no token → `403 {"error":"bad token"}`. To see a PR waiting on you in the page (a fixture copy has no PR), put a stub `gh.exe` in a temp folder first on the API's `PATH`: it answers `auth status` with exit 0, `pr view <n> --json …` with `{"number":<n>,"state":"OPEN","url":"https://github.com/fake/<repo>/pull/<n>","title":"…","headRefOid":"<40 hex>","mergeable":"MERGEABLE","mergeStateStatus":"CLEAN","statusCheckRollup":[],"autoMergeRequest":null}`, `pr list` with `[]`, `api graphql` with `{"data":{"repository":{"pullRequest":{"mergeQueueEntry":null}}}}`, and `pr merge` by writing a marker so the next `pr view` says `MERGED` (on Windows, compile one with `C:\Windows\Microsoft.NET\Framework644.0.30319\csc.exe`). It never reaches GitHub. For the flow's Staging → main step, have it answer `pr list --head <plan-slug>` with a merged final PR whose `baseRefName` is `pod-staging`, and `pr list --head pod-staging` with an open PR into `main` (and give `pr view` a `baseRefName`); the board asks for the staging branch once the plan's sprints are done or its final PR is known. The action log is `<tmp>/cfg/actions.jsonl`. It doesn't exist until the first merge, so a smoke run has none; `/api/board` shows `"actions":[]`. To check that the log is read at start, put a line such as `{"at":1,"action":"merge","repoId":"x","repo":"r","target":"PR #1","result":"stale"}` in that file, restart the API, and find it in `/api/board`'s `actions`.
- **Answer route (on a fixture copy only, never a real repo's queue):** register the copy, then take an answerable entry's `line` from `/api/board` (`repos[].model.queue[]` with `isPending` and `needsYou` true, type `PENDING` or `BLOCKED`, no `answer`). Build the body with a tool, since the line holds backticks and quotes: `jq -n --arg id <id> --arg line "<line>" '{repoId:$id,line:$line,text:"smoke answer"}' > <tmp>/body.json`. `curl -s -X POST http://127.0.0.1:<api>/api/actions/answer -H "Origin: http://127.0.0.1:<api>" -H "Content-Type: application/json" -H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)" --data-binary @<tmp>/body.json` → `200 {"outcome":"answered","logged":true}`. Then `grep "Answer (human)" <tmp>/<copy>/pod-docs/handoff-queue.md` shows it at the end of that line. The same request again → `404 {"error":"not waiting on you"}`; with no token → `403 {"error":"bad token"}`.
- **Resume and auto-continue routes (never the real `claude`, never a real session):** start the API with `OPENAFLOW_CLAUDE_BIN=<tmp>/missing/claude` (a path that doesn't exist) and `OPENAFLOW_CLAUDE_DIR` an empty temp folder, and register a fixture copy. With no transcripts, no run has a session. `curl -s -X POST http://127.0.0.1:<api>/api/actions/resume -H "Origin: http://127.0.0.1:<api>" -H "Content-Type: application/json" -H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)" -d '{"repoId":"<id>","run":"<plan slug>","reply":"try"}'` → `400 {"error":"bad request"}`; `"reply":"go"` on a plan with a started sprint → `404 {"error":"not waiting on you"}`; a sendable reply → `404 {"error":"no session"}`; no token → `403 {"error":"bad token"}`. The toggle: `-d '{"repoId":"<id>","run":"<plan slug>","on":true}'` to `/api/actions/auto-continue` → `200 {"on":true}`, then `<tmp>/cfg/auto-continue.json` holds it under the repo's path and `/api/board` shows `"autoContinue":[{"repoId":"<id>","run":"<plan slug>"}]`, also after a restart; a run that isn't listed → `404 {"error":"not a run"}`. To drive a send as well, put `packages/server/test/fake-claude.mjs` behind `OPENAFLOW_CLAUDE_BIN` (on Windows an npm-style `claude.cmd` beside it: `SET dp0=%~dp0` then `"%dp0%\fake-claude.mjs" %*`), and in the temp claude folder give the plan one ended engineer under `projects/<projectDirName(repo)>/<session>/subagents/` plus `<session>.jsonl`, all modified over 60 s ago, with `"cwd":"<repo path>"` on a record of `<session>.jsonl` (with no such `cwd`, the run offers no send). A sendable `continue` → `200 {"outcome":"started","logged":true}`, and `/api/board`'s `actions` shows `<plan> · continue` started. Touching `<session>.jsonl` → `409 {"error":"session is busy"}`.
- **Add a repo:** `curl -s -X POST http://127.0.0.1:<api>/api/repos -H "Origin: http://127.0.0.1:<api>" -H "Content-Type: application/json" -H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)" -d '{"path":"<absolute repo path>"}'` → `201 {"path":"…"}`; again → `409`; no token → `403 {"error":"bad token"}`. It lands in `<tmp>/cfg/config.json`. A claim file also adds a repo: `<tmp>/ports/3100` holding `<repo path> <plan slug>`. In the page, `Add repo` opens a path field in a modal in the browser build (Add stays off while it's blank; a refused path shows the error, such as `Already registered.`); the desktop shell opens the Windows Select Folder dialog instead, which automation can't reach. Both post the same request.
- **Forget run (temp ports folder only, never the real `%TEMP%\pod-ports`):** register a fixture copy, then write a leftover one-off claim: `<tmp>/ports/3100` holding `<copy path> task-smoke`. `/api/board` lists the run `task-smoke`. `curl -s -X POST http://127.0.0.1:<api>/api/actions/forget-run -H "Origin: http://127.0.0.1:<api>" -H "Content-Type: application/json" -H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)" -d '{"repoId":"<id>","run":"task-smoke","portBase":3100}'` → `200 {"outcome":"removed","run":"task-smoke","portBase":3100,"logged":true}`; `<tmp>/ports/3100` is gone, the run is off `/api/board`, and `actions` starts with a `forget-run` entry, also after a restart. The same request again → `404 {"error":"not a run"}`; `"portBase":0` → `400 {"error":"bad request"}`; a live plan's claim (`<tmp>/ports/3200` holding `<copy path> sparring-ladder`, the copy's active plan; an archived plan's claim gives `404 {"error":"not a run"}`) with `"run":"sparring-ladder","portBase":3200` → `404 {"error":"still listed"}`, and the file stays; no token → `403 {"error":"bad token"}`.
- **Folder listing (gone):** `curl -s -i http://127.0.0.1:<api>/api/fs/folders -H "X-OpenAFlow-Token: $(cat <tmp>/cfg/session-token)"` → `404 {"error":"not found"}`, with or without the token, in dev and in production. Add repo takes a path from the desktop shell's folder dialog or the browser build's path field.
- **Key URLs:** web app `http://127.0.0.1:<web>/` (screen 1: the sidebar (title, runs list, `Add repo`), and the selected run's header, its flow, the Next step card, and tabs, all closed until you open one; the open tab is kept in `localStorage` `openaflow-tab`; `#/<repoId>/<plan>` picks a run, `#/<repoId>` a repo with no plan; `#/<repoId>/<plan>/board` is that run's wave board (screen 2, reached from `Open the wave board` in the run header, with `Back to the run`: dependency lines with the critical path in the accent, filter chips), and `#/<repoId>/<plan>/board/<code>` opens slice `<code>` on it (screen 3: the engineer view under the board, with its details and a live timeline, or `No engineer has started on this slice yet.`); a one-off run (a claim `<repo path> task-<slug>` from `/pod:task`, or `fix-<slug>` from older pod's `/pod:fix`, naming no plan) is `#/<repoId>/<claim name>`, with no wave board, and `#/<repoId>/fix-<slug>/agent/<agentId>` opens one of its engineers in the Log tab; `Add repo` opens the Windows Select Folder dialog in the desktop app and a path field in the shared modal in the browser build; both post to `/api/repos`; stop the API and the sidebar shows `lost · retrying` within about 5 s, and nothing once it's back); API health `http://127.0.0.1:<api>/api/health` → `{"ok":true}`, also through the web proxy at `http://127.0.0.1:<web>/api/health`; the Board `http://127.0.0.1:<api>/api/board` (each repo with `model.plans`, `agents`, `prs`, `claims`, and the Board's `actions`: the action log, newest first, at most 50); one agent's tool timeline `http://127.0.0.1:<api>/api/agents/<repoId>/<agentId>/timeline` → `200 { agentId, events, total, tests }` (names and short summaries only), or `404 {"error":"not found"}` for an agent not on the Board; live updates `curl -sN http://127.0.0.1:<api>/api/events` (an `event: board` at once, another within a few seconds of editing a sprint doc in a watched repo, `: ping` every 15 s). Any other `Host` (say `curl -H "Host: evil.example"`) → `403 {"error":"forbidden host"}`.
