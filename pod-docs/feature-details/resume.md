# Resume

## What it is

The board can send `continue` or `go` to a pod run's own Claude session, so you don't paste the reply into the chat. It runs `claude -p --resume <session> <word>` with your own login. A send starts from a Continue or Go button, or, for `continue` only, from the automatic check when the run's `auto-continue` toggle is on. Every send goes in the action log. Server side: `packages/server/src` (resume routes, auto-continue, toggle store, session activity, claude runner). Which reply may be sent is the model's rule in [queue-and-replies.md](queue-and-replies.md); the buttons and the switch are in [runs-and-pipeline.md](runs-and-pipeline.md).

## How it works

- **Resume route** (`POST /api/actions/resume`, behind the action guard). Checks in order, nothing runs before all pass: `reply` is `continue` or `go` (so `try` is never sent); the model's sendable rule allows it on this run (`404 not waiting on you`); a session with a safe id exists (`404 no session`); the session is idle (`409 session is busy`); no resume for it is in flight (`409 resume in progress`). Then the runner starts, one `auto: false` entry is logged, and the Board is rebuilt.
- **Sendable signals:** `continue` on `wave-merged`, `sprint-done`, `final-merged`, `fix-merged`, and `answered` (you answered a stopped run's entries and no `BLOCKED` of it is unanswered); `go` on `not-started` ([queue-and-replies.md](queue-and-replies.md)). The idle check below applies to each.
- **Where you press it:** Continue or Go on a reply (the Next step card or a Waiting row); the Auto-continue switch for the selected run in the bar's ⋯ menu.
- **Toggle route** (`POST /api/actions/auto-continue`): on, off, or on again (which clears the saved stop key, the way to retry a failed send). Only for a listed run. Not logged.
- **Old fix merges:** the automatic check sends `fix-merged` only within 30 minutes of the merge (`autoMaySend`), and never with no merge time. A merged fix run stays listed until cleanup, so its session can be days old. After that the run still shows Continue, and the card and toast treat it as yours to press ([decision](../decisions.md#2026-11-05--a-merged-fix-run-stays-listed-until-cleanup-human-decision)). The key rules are unchanged: a sent key never sends again. Also, a claimed run keeps Continue while its session is inside the 30-day transcript window: past it, no session is on the Board, so the route answers `no session` and no button shows.
- **Toggle store:** `<config dir>/auto-continue.json`, written to a temp file and renamed. Each toggle keeps `lastKey`; `lastFailed` when the last send of it, by the check or a press, failed to start (a start of any send clears it); and `answeredKeys`: the newest 20 `answered` keys sent, by a press or the check, which the check never sends again. An unreadable file means all off. `Board.autoContinue` lists the toggles that are on.
- **Idle session:** the session's main transcript and every file under `<session>/subagents/` were last modified at least 60 s ago. A missing main file or a time ahead of the clock is busy. Only stats; no transcript is opened.
- **Automatic check:** at start, on every new Board, and every 15 s. It asks the model for the sends due now, holds each session, saves the stop key, starts the runner with `continue`, logs one `auto: true` entry whatever the result, and rebuilds the Board. The route and the check share one hold, so the board never runs two resumes on one session.
- **One owner:** one server per config folder runs the automatic check, through `<config dir>/auto-continue-owner.json` (`{ pid, id, startedAt }`, `id` random per server; dev and production both use it; `owner-file.ts`):
  - **Take:** after the bind, right before the check starts, with an exclusive create. A server that can't start never holds it.
  - **Other holder alive** (`process.kill(pid, 0)`; `EPERM` counts as alive), and it started no later than the file's `startedAt` (2 s of slack for a clock step): this server runs with no automatic check and logs one line naming the holder's process ID and the config folder. It looks only at start, so it stays off until restart, also after the owner exits.
  - **Can't tell** (a live holder, but the file has no usable `startedAt`, or the start time can't be read: not Windows, no `SystemRoot`, WMI unavailable, or the 5 s limit): the same, and the line says so. A double `continue` is worse than no `continue`.
  - **Stale** (the process is gone, the live process started after the file's `startedAt`, so its ID was reused, or the file holds bad JSON or a bad shape): removed and created again, with no log line. Losing that race reads as another holder.
  - **Before each check, the owner re-reads the file.** Another `id` → it stops sending for good and logs one line. File gone or bad → it creates the file again. Any other read error → that check sends nothing, one line is logged per spell of errors, and the next check reads again.
  - **Any other error at take:** no automatic check, and one log line.
  - **Release:** at the end of a normal stop, after the drain, only when the file holds its own `id`. A failed release or a forced quit leaves a stale file, which the next start takes over.
  - **Not covered:** Continue and Go buttons and the toggle route act as today on both servers. A toggle changed on the second server's page reaches the owner only at its next start.
- **Runner:** `OPENAFLOW_CLAUDE_BIN`, else `claude` on `PATH`, always started by its absolute path: only absolute `PATH` entries count, never the repo folder or `.`, and a shim that needs cmd.exe gets an absolute one (`COMSPEC`, else `%SystemRoot%\System32\cmd.exe`). Arguments exactly `-p --resume <session> <word>`. The child env drops every `ANTHROPIC_*` and every `CLAUDE*` variable (`CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_PID`, any case) except three exact names: `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_GIT_BASH_PATH` (only as an absolute path), and `CLAUDE_CODE_MAX_OUTPUT_TOKENS`; `OPENAFLOW_*`, `HOME`, `USERPROFILE`, `APPDATA`, and the rest pass on. `PATH` keeps only its absolute entries, and on Windows `NoDefaultCurrentDirectoryInExePath=1` is set, so neither cmd.exe (for a shim the runner can't read, such as pnpm's `@node "%~dp0…"`) nor claude's own children start a same-named file from the repo folder. Detached, with one stderr log per start in `<config dir>/resume-logs`. In production the runner reads the tool finder at each start ([server.md](server.md)): `OPENAFLOW_CLAUDE_BIN` is that value only, with no search, then a path in settings, then the searches. No found `claude` is a failed start with no spawn, and the child's `Path` is the merged one, with the same rules on top. `started` means still running after 10 s, or exited 0.
- **Which node runs a shim:** an npm `.cmd` shim that names a script runs with the shim's own `node.exe`, else `node` on the child's `Path`, else the fallback. The fallback is the server's own `process.execPath` under plain Node and none under Electron, where that path is Electron's exe and would open an app. With no node, the start answers `failed` with `node not found` and starts no process. A native `claude.exe` needs no node, and a shim the runner can't read keeps its cmd.exe path. The runner never sets `ELECTRON_RUN_AS_NODE`: a packaged build may turn it off.

## Why it's this way

- **The spike first** ([research](../research/resume-spike.md)): resume-runs began by checking that headless resume works with your own login and that Anthropic's rules allow it ([decision](../decisions.md#2026-10-22--headless-resume-is-allowed-for-your-own-use-agent-default--override-anytime)). It ran on Windows only and its verdict was `go`; a failed spike would have left copy-the-reply as the only way.
- **One sendable rule:** route and buttons both use the model's rule, so the board can't send a reply pod isn't waiting for. `go` only from its button ([decision](../decisions.md#2026-10-21--go-only-from-a-button)).
- **Off by default, per run** ([decision](../decisions.md#2026-10-21--a-continue-toggle-per-run)): it's your session and your usage.
- **The key is saved before the start:** a crash or restart mid-send can't send one stop twice. Trade-off: a failed send isn't retried until you turn the toggle on again, so a broken setup doesn't retry every 15 s. A failed send, by the check or a press, raises its stop as an item again (`lastFailed`) on any run, so the dot stays on until a send starts.
- **The 60 s idle rule:** two processes on one session split the conversation (spike check 3). A turn writes every few seconds, and a foreground subagent writes only under `subagents/`, so those files count too. A terminal left open on the session isn't covered: the board can't see it (spike gap 2).
- **Fail closed:** an unreadable toggle file means off, never on.
- **One owner, by file:** dev and production can share a config folder, and two checks would send one stop twice: each holds its sessions in memory only. A held file with a process ID needs no lock service, and a crash leaves a file that the next start can read as stale ([plan](../plans/windows-app.md#key-decisions)).
- **A stop never ends a run:** the runner's `claude` is detached and outlives the server, whether the server stops by Ctrl+C, by the parent's message, or because the parent died. No tree kill and no Job Object.
- **A manual `continue` saves the key too,** so the automatic check doesn't send the same stop after your press.
- **No Claude or Anthropic env from the board:** a board started inside a Claude Code session would hand the run that session's state (`CLAUDECODE`, `CLAUDE_CODE_*`) or an API key, base URL, or Bedrock/Vertex switch, so the run wouldn't be your own login. `CLAUDE_CONFIG_DIR` stays: it names where your login and sessions live, the same folder the board reads transcripts from, and without it `--resume` would look in `~/.claude` and not find the session. `CLAUDE_CODE_GIT_BASH_PATH` and `CLAUDE_CODE_MAX_OUTPUT_TOKENS` stay too: they are machine settings a shell may hold alone, and a run can fail to start without them.

## Watch out

- **Setup: a permission mode.** A resumed `claude -p` run can use tools only if your settings give it a permission mode (for example `"defaultMode"` in `~/.claude/settings.json`). Without one it denies tool calls and the orchestrator stalls. The runner never passes a permission flag.
- **A terminal still open on the session** doesn't show the board's turn; typing in it after a send splits the conversation. Reopen with `claude --resume <id>`.
- **`--bare`:** the headless docs say it will become the default for `-p`. Bare mode never reads your login, so a resume would fail; the runner must never pass an API key instead.
- **Your hooks run:** a `Stop` or `Notification` hook fires once per send.
- **A quiet turn:** one long tool call can leave every file quiet for over 60 s; a send then happens only if pod also shows a sendable stop.
- **A toggle names a path, not an id:** `repoPathKey` (the normalized path, case-folded where the file system ignores case). An id changes when a clash forms or ends, and another repo can take it, so never match a toggle by id. A toggle with no path (saved before this rule) reads off and sends nothing; it leaves the file at the next toggle change. Remove always forgets it, also for a repo a port claim still lists, so adding the folder again, or a claim ending, turns nothing back on. With no Remove, a claim-only repo whose claim ends reads off and reads on again when the claim comes back: the toggle was never turned off.
- **A session must be provably the repo's:** Claude's project folder is shared by paths that differ only in symbols. A send needs a session whose own `<session>.jsonl` has its first `cwd` in the repo (`sessionUnproven` in `server.md`). Where its agents work doesn't count. A session file with no readable `cwd`, or one that started elsewhere, gets no Continue, no Go, and no automatic send.
- **Unlisted runs:** the toggle route answers `404 not a run`, even to turn it off; such a toggle stays in the file but never sends.
- **A `claude` on a relative `PATH` entry is skipped:** a `PATH` with `.` or `bin` in it would resolve against the repo folder the run starts in. Put `claude`'s folder on `PATH` as an absolute path, or set `OPENAFLOW_CLAUDE_BIN`. In production `OPENAFLOW_CLAUDE_BIN` must be an absolute path: a bare name reads as `bad-path`.
- **The start-time lookup costs about 0.8 s at a server's start.** It starts Windows PowerShell by its absolute path, with no window, and only when a live process holds the file. It reads `Win32_Process`, because `Get-Process` gives no start time for another account's process unless elevated. It blocks the start for up to 5 s.
- **Outside Windows, a reused process ID still reads as alive.** There is no lookup there, so the server logs `can't read when it started` and stays off until that process ends or you delete the file. The page shows no sign of this.
- **`node not found` in the desktop shell:** an npm-installed `claude` needs a Node on `Path`, because Electron's exe never stands in for one. Install Node or use the native `claude.exe`.
- **The kept env names are an exact list, never a prefix:** `CLAUDE_CODE_*` also holds `CLAUDE_CODE_OAUTH_TOKEN` and session state. Add a name only if it is a machine setting. A setting that holds a path to run must be absolute, or it resolves in the repo folder the run starts in.
- **Tests and smoke runs** use a fake runner or `packages/server/test/fake-claude.mjs` and a temp config, never the real `claude` or `auto-continue.json`. The runner keeps the newest 20 `.log` files in `resume-logs/` and deletes older ones when it starts a run; a log a running child still holds open on Windows is kept until a later start.
