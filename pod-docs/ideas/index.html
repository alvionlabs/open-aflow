Clean up a leftover run

parked

The idea

A Clean up this run item in a leftover run's ⋯ menu. It does what pod's own cleanup does after a merge: it removes the run's worktree (git worktree remove), deletes the local branch with git branch -d (which refuses an unmerged branch), and deletes the port claim file. It uses no force. If a step fails, it stops and says which step failed. Forget this run (ui-rework plan) only deletes the claim file and leaves the worktree and branch on disk.

Why it waits

's on hold

The human chose Forget only on 2026-11-12. Clean up would be the board's first git write in a repo, against the rule that the board writes only the queue file (actions.md). Worktree removal also fails often on Windows when a file is locked (known issue).

Worth building when

it worth building

Leftover worktrees and branches pile up after Forget, and removing them by hand becomes a chore. It needs a decision that lets the board run these git commands.

Native desktop stack after Electron

parked

The idea

Replace the Electron shell and the React UI with a native UI on Windows, Linux, and macOS. GPUI with gpui-component is the first candidate, and Iced is the fallback.

Discord is a reference. On 2026-11-04, its CTO confirmed a Rust rebuild on GPUI that removes Electron and React Native. Discord had no release date or public test then.

A UI rewrite alone leaves the Node server running, so its memory stays. To remove Node, also rewrite the server, the file watching, and the git, gh, and claude process handling.

Why it waits

's on hold

We ship Electron now because shipping fast matters more. We have no RAM measurement of openaflow that shows a problem. Discord's 290 MB figure is one screenshot of an early build, not a benchmark. GPUI's API still changes, and it has no built-in text input.

Worth building when

it worth building

All of these must be true, in this order:

  • A measurement of the installed app, with the window open and in the tray, shows RAM use that is too high.
  • Fixes to the app do not solve the problem, and Electron's UI layer is the measured cause.
  • A two-day GPUI test passes on Windows, Linux, and macOS. The test covers the hardest board screen, one tray icon, and one notification.

Discord's public build can also give real numbers for this decision.

Sort the runs list by most recent activity

planned — pod-docs/plans/ui-rework.md

The idea

Put the run with the most recent activity at the top of the sidebar's runs list. Today listRuns in packages/model/src/runs.ts sorts by state first (blocked, needs you, running, …), then by repo name, then by plan slug. In the 2026-11-12 end-to-end test, the human expected the task run they were working on to come to the top. It read needs you, so three test repos that read blocked stayed above it.

Research on 2026-11-12, by web search, found no formal study. It found two common patterns:

  • Recency as the default for activity lists. For example, Featurebase's inbox shows the most recently updated items at the top.
  • Priority groups with recency inside each group for work queues. For example, Featurebase's "Highest priority" sort, and multi-key sorts such as status, then date.

Users often ask for both, and a list should show which sort is active.

Options:

  • Recency only. The newest activity is on top. Urgency stays visible through the urgent banner and each card's state dot. This matches what the human expected.
  • State groups, newest first inside each group. It keeps blocked runs on top, but it would not have put the test run on top.

The recommendation is option 1, because the urgent banner already raises the most urgent item from any run. Pick a "last activity" time for each run, such as the newest agent write, queue change, or PR event, and keep the order stable while nothing changes.

Sources: Featurebase inbox sorting, Wrike sorting request, Marker.io sorting request, and a Claude sidebar request to order by last activity.

Why it waits

's on hold

The v0.1.0 release comes first. The human picks option 1 or 2, and decides what counts as activity.

Worth building when

it worth building

It's already wanted. Build it with the next UI work after v0.1.0, for example with auto-continue-indicator.md.

CLI runner

superseded by research/terminal-host.md (2026-11-11)

The idea

The board's server runs your own claude binary with your own login:

  • Step in (phase 3): claude in a pseudo-terminal (node-pty), shown in the browser with xterm.js over a WebSocket, so you can type into an engineer's session.
  • Runs without a chat (phase 4): claude -p --resume <session> --output-format stream-json "continue", rendered as board events, to resume after go or continue and start runs from the board.

Never --bare, which needs an API key. The 127.0.0.1 binding, the Host check, and a per-launch token are required from the phase that adds it, since a server that starts claude can run code on the machine.

Why it waits

's on hold

Phase 1 is read-only, and phases 3 and 4 are decided after using phases 1–2. node-pty is a native module with build risk on Windows, and Anthropic's headless billing rules changed several times in 2026.

Worth building when

it worth building

After phases 1–2, stepping into engineers or resuming runs from the board is still the main friction, and Anthropic's current policy allows running the user's own claude this way.
